# 16 — `1.4.0` GLM 双模式统一发布与验收

状态：**RELEASE CANDIDATE — CROSS-PLATFORM AND PUBLIC RELEASE GATES IN PROGRESS**
日期：2026-07-28
基线：`v1.3.0`

## 1. 版本决策

`1.4.0` 在一个 minor release 中同时发布两个 GLM 用户入口：

```text
cmr glm       = GLM Coding Plan
cmr glm-api   = GLM 标准 API按量付费
cmr glm-payg  = glm-api 的唯一别名
```

合并的是版本与发布节奏，不是凭据或费用通道。两个入口继续保持：

| 维度 | `glm` | `glm-api` |
|---|---|---|
| Provider/Profile/Secret ID | `glm` | `glm-api` |
| 鉴权变量 | `ANTHROPIC_AUTH_TOKEN` | `ANTHROPIC_API_KEY` |
| Header | `Authorization: Bearer` | `X-Api-Key` |
| Key 来源 | Coding Plan | 标准 API Keys |
| 费用语义 | 套餐规则 | 标准 API Token 按量计费 |

本决策取代 `docs/15` 中“按量 API 单独预定为 `1.5.0`”的版本安排，但不改变 `docs/14`、`docs/15` 已验收的运行时、安全与隔离合同。保留两个实施文档原文件名，避免删除或重命名历史规格。

## 2. 发布范围

- 四个正式 Provider/Profile：`kimi`、`deepseek`、`glm`、`glm-api`。
- 三条 Pricing：`kimi-k3`、`deepseek-v4`、`glm-5.2`。
- `glm-5.2` 与 `glm-plan` 继续只解析到 Coding Plan。
- `glm-payg` 只解析到标准 API 按量入口。
- 两种 GLM 鉴权变量大小写安全清理，每次只向子进程注入当前 Provider 的一种凭据。
- 旧 Secret Store Schema v1 无迁移可读；写入新 Provider 后仍保持原子更新和 fail closed。
- 新 Provider 通过 Setup State 差集触发一次全量 onboarding，不引入版本特判。
- `glm-api` 启动时显示数据化的直接按量计费提示；`glm` 不显示按量提示。
- Claude argv、cwd、TTY、信号和退出码合同不变。
- `1.3.0` 自更新、回滚与固定 Release 资产通道不变。

明确不做：

- 不合并或复制两把 GLM Key。
- 不检测 Key 类型。
- 不查询余额、额度或费用明细。
- 不在 Plan 与 PAYG 之间自动 fallback 或重试。
- 不新增代理、SDK、运行时依赖或生命周期脚本。

## 7. Release staging

固定资产：

```text

```

发布顺序：

1. 从 exact release commit 在仓库外构建 `npm pack`。
2. 固定命名并生成 SHA-256。
3. 从固定资产安装到全新临时 prefix，验证 `cmr version` 和 help。
4. 推送 `main` 与 annotated tag `v1.4.0`。
5. 先创建 Draft Release 并上传两项资产。
6. 下载 Draft 资产，核对字节、checksum 与隔离安装。
7. 发布 immutable Latest Release。
