## 0. 一页结论

### 0.1 本轮只新增一个显式按量入口

规范入口：

```bash
cmr glm-api [claude args...]
```

唯一兼容别名：

```bash
cmr glm-payg [claude args...]
```

绑定语义：

```text
Provider ID=glm-api
Profile ID=glm-api
Display name=GLM-5.2 API (Pay-as-you-go)
Base URL=https://open.bigmodel.cn/api/anthropic
authVariable=ANTHROPIC_API_KEY
Claude Code header=X-Api-Key
secretId=glm-api
API Key page=https://bigmodel.cn/usercenter/proj-mgmt/apikeys
billing=智谱标准 API 按量计费
```

既有入口保持原义：

```text
cmr glm       = GLM Coding Plan
cmr glm-api   = GLM 标准 API 按量付费
```

两者绝不自动互相切换。

### 0.2 本轮已经替 Terra 做出的产品决策

Terra 不需要重新解释以下问题：

1. 目标版本使用 `1.5.0`，不把标准 API 挤进 `1.4.0` 的 Coding Plan 合同。
2. `glm-api` 是独立 Provider、Profile 和 Secret Store 槽位。
3. `glm-payg` 是唯一别名；不新增 `zhipu-api`、`glm-standard` 等同义入口。
4. 既有 `glm-5.2` 与 `glm-plan` 继续解析到 Coding Plan `glm`，不得改绑到按量入口。
5. 按量与 Plan 复用相同 Anthropic 兼容 Base URL，但使用不同鉴权变量和 Header。
6. 按量 Profile 初始模型映射复用当前已核验的 GLM Claude Code 档位映射：
   - Opus/Sonnet → `glm-5.2[1m]`
   - Haiku → `glm-4.7`
7. `glm-api` 复用现有 `config/pricing/glm-5.2.json`，不复制同一价格事实。
8. `glm-api` 每次启动显示一行“标准 API 直接按量计费”警告，但不增加 `[y/N]` 二次确认。
9. `glm-api` 作为第四个正式 Provider，按现有 unseen Provider 机制触发一次全量 onboarding；用户可选择 Not now，不强制配置两把 GLM Key。
10. 不实现 Key 类型检测、余额查询、用量查询、费用估算、Plan 超额按量、自动 fallback 或失败重试代理。

### 0.3 为什么必须是两个 GLM Provider

官方当前事实：

| 项目 | `glm` Coding Plan | `glm-api` 标准 API |
|---|---|---|
| Base URL | `https://open.bigmodel.cn/api/anthropic` | `https://open.bigmodel.cn/api/anthropic` |
| Claude Code 凭据变量 | `ANTHROPIC_AUTH_TOKEN` | `ANTHROPIC_API_KEY` |
| Header | `Authorization: Bearer` | `X-Api-Key` |
| Key 来源 | Coding Plan 套餐入口 | 智谱开放平台 API Keys |
| 费用语义 | 套餐/套餐规则 | 标准 API Token 价格 |
| CMR Secret | `glm` | `glm-api` |

相同 URL 不能证明 Key、Header 或账单通道相同。把两把 Key 存进一个槽位会导致替换、撤销、诊断和费用责任全部变得模糊。

### 0.4 当前发布依赖

`1.5.0` candidate 依赖当前工作区的 `1.4.0` candidate，但不消除它的未完成门禁：

```text
1.3.0 stable/released
  └── 1.4.0 GLM Coding Plan candidate
        └── 1.5.0 GLM standard API PAYG candidate
```

在以下项目完成前，不得发布 `1.5.0`：

- `1.4.0` Coding Plan 自身 Blocker 全部闭环。
- `glm-api` 假 Key、跨平台、打包与独立审阅通过。
- 用户授权的真实标准 API Key 最小请求、工具、子 Agent 与费用明细回读通过。
- 实际 Windows OS 回归通过。
- 用户另行批准 commit、push、CI、tag 与 Release。

Terra 正常交回状态应为：

```text
TERRA_IMPLEMENTATION_COMPLETE — AWAITING_CODEX_REVIEW
```

不是 PASS，也不是 RELEASED。

### 2.2 标准 API 鉴权

智谱 Claude API 兼容文档当前明确：

```text
Base URL=https://open.bigmodel.cn/api/anthropic
API Key environment=ANTHROPIC_API_KEY
HTTP header=x-api-key
native model example=glm-5.2
```

Claude Code 官方环境变量文档当前明确：

```text
ANTHROPIC_API_KEY  -> X-Api-Key
ANTHROPIC_AUTH_TOKEN -> Authorization: Bearer <value>
```

因此 `glm-api` 的 Provider 目标必须是：

```text
authVariable=ANTHROPIC_API_KEY
```

不得用 `ANTHROPIC_AUTH_TOKEN` 仅因为智谱原生 OpenAI 兼容 API 的示例使用 Bearer；本功能连接的是 Anthropic 兼容端点，必须按该端点和 Claude Code 的 `X-Api-Key` 合同实现。

### 2.3 模型与上下文

当前官方事实：

```text
GLM-5.2 native model ID=glm-5.2
GLM-5.2 context=1,000,000 tokens
GLM-5.2 maximum output=128K tokens

GLM-4.7 native model ID=glm-4.7
GLM-4.7 context=200,000 tokens
GLM-4.7 maximum output=128K tokens
```

Claude Code 官方文档明确：

- 自定义/第三方 Base URL 下，Provider 定义实际模型名。
- `ANTHROPIC_DEFAULT_*_MODEL` 可把 Claude 档位映射到 Provider 模型。
- 支持 1M 的模型可在 Claude Code 选择层追加 `[1m]`。
- Claude Code 在向 Provider 发送请求前剥离 `[1m]`。

因此必须区分：

```text
Claude Code 选择层：glm-5.2[1m]
智谱上游 API model：glm-5.2
```

CMR 不自己剥离后缀，也不建立代理。

### 2.4 标准 API 价格

智谱价格页当前列出 GLM-5.2：

```text
普通输入=8 CNY / million tokens
输出=28 CNY / million tokens
缓存命中=2 CNY / million tokens
缓存存储=限时免费（活动事实，不能承诺长期有效）
```

现有 `config/pricing/glm-5.2.json` 已记录前三项稳定单价与核验日期。本轮复用该记录，不在第二个 JSON 中复制。

GLM-4.7 的价格按输入/输出长度分档。初始运行时警告不尝试计算 GLM-4.7 精确价格；使用文档必须明确 Haiku 档会产生独立的 GLM-4.7 标准 API 费用，并引导查看同一官方价格页。

CMR 不记录 Token，不计算会话费用，不查询资源包或余额。

### 2.5 “同一模型映射”是设计决策，不是假装成官方原文

官方没有给出一份单独命名为“标准 API Key + Claude Code”的完整六变量 Profile。当前存在两组可核验事实：

1. 标准 Claude API 兼容文档明确 Base URL、`ANTHROPIC_API_KEY`、`X-Api-Key` 和 `glm-5.2`。
2. 智谱当前完整 Claude Code 文档明确 Opus/Sonnet/Haiku 的 GLM 映射与 compact/timeout/traffic 变量。

本合同据此做出最小推断：`glm-api` 初始环境复用 `glm` 的公开模型与运行变量，只替换 Provider 鉴权边界。

这项推断必须由以下证据约束：

- 配置与假 Claude 精确快照。
- 真实标准 API Key 直连接口验证。
- 真实 `cmr glm-api` 主请求、工具和子 Agent。
- 智谱费用明细回读，证明走标准 API。

如果真实证据显示标准 API 不接受该映射，Terra 不得临时加变量或换模型。必须先更新 `docs/07`、本文和目标 JSON，经用户确认后再改代码。

### 2.6 Coding Plan “超额按量”不是本功能

当前智谱错误码页面出现 1316–1321 等“无法使用超额按量付费”的文案，说明部分 Coding Plan/团队套餐可能存在受余额或预算约束的超额机制。它不改变本轮边界：

- `glm-api` 使用标准平台 API Key。
- `glm` 仍使用 Coding Plan Key。
- CMR 不开启、关闭、探测或代理 Plan 超额功能。
- CMR 不因 Plan 额度错误切到 `glm-api`。
- CMR 不因标准 API 欠费切回 `glm`。

若 `docs/14` 或 `docs/07` 中“Plan 绝不会产生任何超额按量”的旧表述与实施日官方页面冲突，Terra 应先更新事实文档，准确写成“CMR 不自动切换；具体套餐超额规则以用户账户与官方当日规则为准”，再继续代码。

```bash
cmr glm-api --help

```

Profile 选择器后的全部参数保持顺序和值，原样传给 Claude Code。

### 3.2 名称与别名

规范 ID：

```text
glm-api
```

唯一别名：

```text
glm-payg
```

不得新增或改绑：

```text
glm
glm-5.2
glm-plan
zhipu-api
glm-standard
payg
```

`glm-5.2` 目前是 Coding Plan `glm` 的兼容别名。虽然名称不够区分计费模式，但修改它会破坏当前候选合同和用户脚本，本轮保持兼容。

### 3.3 鉴权与环境

Provider 注入：

```text
ANTHROPIC_BASE_URL=https://open.bigmodel.cn/api/anthropic
ANTHROPIC_API_KEY=<GLM standard API key>
```

Profile 注入：

```text
ANTHROPIC_DEFAULT_OPUS_MODEL=glm-5.2[1m]
ANTHROPIC_DEFAULT_SONNET_MODEL=glm-5.2[1m]
ANTHROPIC_DEFAULT_HAIKU_MODEL=glm-4.7
CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
API_TIMEOUT_MS=3000000
```

`glm-api` 子进程必须没有：

```text
ANTHROPIC_AUTH_TOKEN
ANTHROPIC_MODEL
ANTHROPIC_DEFAULT_FABLE_MODEL
CLAUDE_CODE_SUBAGENT_MODEL
CLAUDE_CODE_EFFORT_LEVEL
ENABLE_TOOL_SEARCH
```

这些否定断言与当前 `glm` 保持一致。不要因为标准 API 是按量计费，就自行给它增加更多 Claude Code 行为变量。

### 3.4 启动费用提示

每次 `glm-api` 启动，在 spawn Claude 前输出一行：

```text
WARN  GLM-5.2 API (Pay-as-you-go) uses direct standard API billing; CNY/M GLM-5.2 tokens: cache hit <value>, input <value>, output <value>; other mapped models may have different rates; verified <date>.
```

要求：

- 数值与日期读取 `config/pricing/glm-5.2.json`。
- 不在 JS 中复制 2/8/28。
- 明确出现 `Pay-as-you-go` 或 `direct standard API billing`。
- 不估算本次会话费用。
- 不读取余额。
- 不显示 Key。
- 不增加 CMR 自己的确认提示。

Claude Code 官方说明：交互模式首次检测到 `ANTHROPIC_API_KEY` 时，可能要求用户确认是否使用该 API Key 覆盖当前订阅。该提示属于 Claude Code，CMR 不拦截、不代答、不伪装成 CMR 提示。非交互 `-p` 有 Key 时会使用该 Key。

### 3.5 Setup 与 onboarding

新增第四个正式 Provider 后：

- 全新用户首次 `cmr` 显示 Kimi、DeepSeek、GLM Coding Plan、GLM API 四家状态。
- 已 seen 三家的 `1.4.0` 用户因为 `glm-api` unseen，再显示一次全量 onboarding。
- 用户可以 Not now；不得强制配置 `glm-api`。
- `Configure all missing` 是用户明确选择，才依次处理所有缺失 Provider。
- `cmr setup glm-api` 只处理 `glm-api`，不把其他未显示 Provider 标为 seen。
- `cmr glm-api` 缺 Key + TTY：就地配置 `glm-api`，成功后继续原 argv。
- 缺 Key + non-TTY：快速失败，并提示 `cmr secret set glm-api`。
- `cmr secret set glm-api` 与 `cmr secret status` 必须支持第四槽位。

不得增加 `optionalProvider`、`onboardingVersion` 或包版本特判。本轮直接复用已验收的动态 unseen Provider 机制。

### 3.6 不做自动 fallback

以下行为全部禁止：

```text
glm 失败 -> glm-api
glm-api 失败 -> glm
Bearer 失败 -> X-Api-Key 重试
X-Api-Key 失败 -> Bearer 重试
Coding Plan 用量满 -> 标准 API
标准 API 欠费 -> Coding Plan
根据 Key 前缀猜类型
把同一 Key 同时放进两种变量
```

用户必须通过命令显式选择本次费用通道。

## 6. 关键架构决策

### 6.1 独立 Provider/Profile，复用通用启动路径

`glm-api` 的差异全部由数据表达：

```text
provider.authVariable
provider.secretId
provider.apiKeyUrl
profile.displayName/purpose/costNotice
```

`environment.js` 已通过：

```js
environment[provider.authVariable] = secret;
```

支持两种合法鉴权变量。不得为 `glm-api` 新建启动函数或在 launcher 中加 Provider 分支。

### 6.2 环境映射与 Plan 相同，鉴权边界不同

测试必须同时证明：

```js
glm.environment deepEqual glmApi.environment
glm.provider !== glmApi.provider
glm authVariable === "ANTHROPIC_AUTH_TOKEN"
glmApi authVariable === "ANTHROPIC_API_KEY"
glm secretId === "glm"
glmApi secretId === "glm-api"
```

这样可以防止未来把“相同模型映射”错误理解为“共享一把 Key”。

### 6.3 `costNotice=payg`

当前 validator 只允许：

```text
high
standard
```

本轮扩展为：

```text
high
standard
payg
```

语义：

- `high`：现有高费用价格意识提示。
- `standard`：不额外提示。
- `payg`：明确标准 API 直接按量计费。

不要把 `glm-api` 伪装成 `high`，也不要通过 `profile.id === "glm-api"` 决定是否警告。计费提示必须由数据化 `costNotice` 驱动。

### 6.4 Pricing 一对多引用

Validator 已允许多个 Profile 引用同一 pricing ID。本轮应新增正向测试，证明：

```text
glm -> glm-5.2
glm-api -> glm-5.2
```

不要把配置集合错误约束为 “profiles.length === pricing.length”。

### 6.5 仍使用 Secret Store Schema v1

旧三家文件：

```json
{
  "version": 1,
  "providers": {
    "kimi": "test-kimi-key",
    "deepseek": "test-deepseek-key",
    "glm": "test-glm-key"
  }
}
```

在 `1.5.0` 中必须：

- 可读。
- `glm-api` 状态为 missing。
- `set("glm-api", ...)` 后前三项值不变。
- 写入失败时原文件字节不变。
- 不自动复制 `glm` Key 到 `glm-api`。

### 6.6 Setup State 继续用差集

旧状态：

```json
{
  "version": 1,
  "seenProviderIds": ["deepseek", "glm", "kimi"]
}
```

新配置自然得到：

```text
unseenProviderIds=["glm-api"]
```

完成或 Not now 后：

```json
{
  "version": 1,
  "seenProviderIds": ["deepseek", "glm", "glm-api", "kimi"]
}
```

保持字典序、并集与原子写入，不增加包版本逻辑。

### 6.7 双鉴权变量的隔离是本轮最高风险

`ROUTER_MANAGED_ENV_VARS` 已包含：

```text
ANTHROPIC_API_KEY
ANTHROPIC_AUTH_TOKEN
```

每次启动先大小写不敏感清理二者，再只注入当前 Provider 的一个变量。

必须覆盖：

```text
glm -> glm-api
glm-api -> glm
glm-api -> kimi
glm-api -> deepseek
kimi/deepseek -> glm-api
```

每一步都断言：

- 选中 Provider 的 auth 存在。
- 另一种 auth 不存在。
- mixed-case 残留不存在。
- 父环境逐键不变。
- Secret 值不进入公开 snapshot。

### 6.8 降级风险

`1.5.0` 写入 `glm-api` 后，`1.4.0`/`1.3.0` 的 Secret Store allowlist 不认识该字段，手工降级可能拒绝整个 Store。

文档必须明确：

- 不为降级自动删除 `glm-api`。
- 不静默忽略未知 Secret。
- 任何备份、编辑、删除或 Key 轮换都需用户批准。
- 自动更新 rollback 不等于跨版本用户数据迁移。
