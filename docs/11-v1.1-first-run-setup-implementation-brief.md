## 1. 目标结果

把当前分散的手工密钥命令编排成一个短、可恢复、可重复进入的终端向导，同时保留现有安全边界。

新用户的最短路径：

```text
安装 cmr
  → 在项目目录第一次运行 cmr
  → 先看到全部当前 Provider 的 configured/missing 状态
  → 无论已有零把、一把或全部 Key，都进入一次引导
  → 选择配置缺失项、更换已有项或稍后继续
  → 打开向导显示的官方页面创建 Key
  → 在终端隐藏粘贴 Key
  → CMR 原子保存到仓库外 Secret Store
  → 回到带状态的 Profile 菜单
  → 选择 Kimi 或 DeepSeek 启动 Claude Code
```

已有用户的维护路径：

```text
cmr setup
  → 看到 kimi/deepseek configured/missing
  → 选择更换某一家 API Key
  → 默认保留旧 Key；显式确认后隐藏输入新 Key
  → 新 Key 校验与原子写入成功后才替换旧 Key
```

直接启动路径：

```text
cmr deepseek --resume session-123
  → DeepSeek Key 缺失且当前是 TTY
  → 只引导配置 DeepSeek
  → 保存成功
  → 继续原命令，argv 仍为 ["--resume", "session-123"]
```

最终版本为 `1.1.0`。这是向后兼容的新增管理能力，但改变了首次无参数运行和缺 Key 交互启动体验，因此使用 minor 版本，不继续标 `1.0.0`。

## 2. 现状排查结论

规划时已确认 `1.0.0` 有以下能力：

- `cmr secret set kimi|deepseek` 使用 TTY raw mode 隐藏输入。
- `SecretStore.set()` 校验空值、首尾空白、换行、NUL 和最大长度。
- Secret Store 位于仓库外；macOS 使用 `0600` 文件和 `0700` 目录。
- 写入使用同目录临时文件与 rename，失败时清理临时文件。
- `cmr secret status` 与 Doctor 只输出 `configured/missing`。
- 启动器缺 Key 时只抛出 `missing ... secret; run cmr secret set ...`。
- 无参数 TTY 菜单只列 Kimi、DeepSeek、Doctor、Exit，不显示密钥状态或 setup。
- 非 TTY 的无参数 `cmr` 打印帮助，不会等待输入。
- 当前没有 `setup`、首次运行检测、Provider Key 官方入口或组合式向导。

所以本次不是重建密钥系统。根本改动是新增一个可测试的 setup 编排层和仓库外非敏感 Setup State Store，并让 CLI 在三个明确入口调用它：

1. Setup State 缺失或当前配置存在 unseen Provider 的无参数 TTY 运行；Key 状态不参与首次判断。
2. 显式 `cmr setup [provider]`。
3. 缺少所选 Provider Key 的交互式 Profile 启动。

## 3. 原始问题与根因

### 3.1 用户问题

用户从 GitHub clone、在公司新电脑安装或由他人下载安装后，不应先阅读内部命令清单，再逐条执行 `secret set/status`。第一次可运行不等于第一次可使用；安装和 Provider 配置之间缺了一段产品化流程。

### 3.2 根因

根因不在存储层，而在入口与状态编排：

- CLI 没有独立的 onboarding 状态，因而无法区分“首次运行但已有 Key”和“老用户日常运行”。
- 把“两家均 missing”当首次会错误跳过已有一把或全部 Key 的新用户，也无法在以后新增 Provider 时重新引导。
- 现有隐藏输入一次只服务一个底层命令。
- Provider 配置没有 API Key 官方控制台 URL。
- 普通菜单不显示哪个 Profile 可立即使用。
- 缺 Key 启动不尝试在当前 TTY 中完成配置并继续。
- 已有安全写入能力没有暴露为“随时更换 Key”的易用管理界面。

只在 README 增加三条命令不是修复；只在缺 Key 错误后加一句更长提示也不是修复。必须同时覆盖配置数据、setup 状态机、CLI 分派、启动衔接、替换事务、终端恢复、测试和文档。

## 4. 范围

### 4.1 必须实现

- 新增 `cmr setup`。
- 新增 `cmr setup kimi` 与 `cmr setup deepseek` 直达入口。
- Setup State 缺失时，无参数 TTY 首次运行无条件显示全部当前 Provider 状态并进入 setup。
- 当前 Provider 集合出现 unseen ID 时，再次显示全量状态并进入 setup。
- 普通菜单从数据化配置显示所有 Provider 的 `configured/missing`，并提供 setup 入口。
- 用户可在 setup 配置所有缺失 Provider、只配置一家、稍后退出。
- 用户可随时在 setup 明确更换 Kimi 或 DeepSeek API Key。
- 已配置 Key 默认保留；替换前二次确认，默认答案为 No。
- 新 Key 本地校验/写入失败或用户取消时，旧 Key 保留。
- Profile 缺 Key + TTY 时，就地配置当前 Provider 并继续原启动。
- 非 TTY 永不进入交互或等待输入。
- Provider JSON 增加官方 `apiKeyUrl`，由配置校验器验证。
- 新增仓库外 `state.json`，只记录 Schema 版本和 `seenProviderIds`；完成或明确选择稍后才原子更新。
- setup 完成后给出脱敏状态、Claude 可执行文件发现结果和下一步。
- 保留 `cmr secret set/status` 兼容入口。
- 版本更新到 `1.1.0`，文档与帮助切换到已实现行为。
- 自动化覆盖 K/L/M/N 全矩阵，并回写本文件第 15 节。

## 5. 关键设计决策

| 决策 | 选择 | 原因 | 禁止的替代 |
|---|---|---|---|
| 触发时机 | 安装后首次交互运行 | TTY、用户意图和错误恢复都可控 | `postinstall` 读 Key |
| 首次定义 | Setup State 缺失或有 unseen Provider | 与 Key 状态解耦，支持已有 Key 和未来 Provider | 用 missing 数量猜首次 |
| State 内容 | `version + seenProviderIds` | 最小非敏感状态，可检测新增 Provider | 完成时间、账号、Key 快照、遥测 |
| 部分配置 | 允许只配置一家 | 用户可能只购买一家 | 强制两家都有 Key |
| `1.0.0` 升级用户 | `1.1.0` 首次运行统一看一次全量状态 | 没有 State 即未完成 onboarding，与已有 Key 无关 | 有 Key 就跳过 |
| 新 Provider | ID 不在 seen 集合则再次引导 | 未来扩展无需另写首次逻辑 | 只按包版本或固定两家判断 |
| 新模型/Profile | 共用既有 Provider Key 时不重触发 | 引导按凭据边界而非模型数量 | 每加模型都弹 onboarding |
| 稍后配置 | 看过全量状态并明确选择后 mark seen | 尊重用户决定且不反复打扰 | 每次启动继续强弹 |
| 维护入口 | `cmr setup` 同时负责新增与更换 | 心智单一，适合非技术用户 | 只保留 `secret set` 专家命令 |
| 替换默认 | 保留旧 Key，显式确认才换 | 防止误操作 | 进入 provider 页面就覆盖 |
| 替换事务 | 新值成功写入后才替换旧值 | 失败可恢复 | 先删除旧 Key 再输入 |
| 存储 | 复用 Secret Store Schema v1 | 已验收、兼容现有用户 | `.env` 或新数据库 |
| Provider URL | `apiKeyUrl` 数据化 | 文案不硬编码两套事实 | CLI `if(provider)` 写 URL |
| Key 格式 | 只用现有通用校验 | Provider 前缀可能变化 | 硬编码 `sk-` 正则 |
| 网络验证 | 首版不做 | 避免代理/离线假失败 | 自动请求 Provider |
| 浏览器 | 只显示 URL | 跨平台、可测试、无外部副作用 | `open/start` 自动执行 |
| 交互实现 | Node 标准库 + 可注入 prompter | 无依赖、便于 fake 测试 | 引入 TUI 框架 |
| Profile argv | 完全 opaque，setup 后原样继续 | 保持核心透明合同 | 为 setup 解析 Claude 参数 |
| 冲突处理 | 只读提示 `cmr doctor` | 不越权改用户配置 | setup 自动迁移 Settings/Shell |
| 版本 | `1.1.0` | 新增用户可见功能且向后兼容 | 继续 `1.0.0` 或升 major |

## 7. 数据与接口合同

### 7.1 Provider `apiKeyUrl`

目标 Kimi Provider 增加：

```json
"apiKeyUrl": "https://platform.kimi.com/console/api-keys"
```

目标 DeepSeek Provider 增加：

```json
"apiKeyUrl": "https://platform.deepseek.com/api_keys"
```

验证规则：

- 字段必填且只允许字符串。
- 可由 `new URL(value)` 解析。
- `protocol` 必须严格等于 `https:`。
- 不允许 username、password、fragment。
- 不允许相对 URL、控制字符或首尾空白。
- 配置基线测试分别断言上述两条当前官方 URL；不得在 validator 业务逻辑中硬编码 Provider 域名。

实施前和准备发布前，必须从 `docs/07-official-sources.md` 的官方文档链接再次点击到控制台，确认没有迁移或重定向到新域名。如果变化，先更新 07 与配置，再更新测试。

### 7.2 Setup State Store

目标路径：

- macOS：`~/Library/Application Support/ClaudeModelRouter/state.json`
- Windows：`%APPDATA%\ClaudeModelRouter\state.json`

必须从 `platform.js` 的统一 CMR 应用数据目录派生，不能分别复制两套路径字符串。目标 Schema：

```json
{
  "version": 1,
  "seenProviderIds": ["deepseek", "kimi"]
}
```

合同：

- 顶层只允许 `version` 与 `seenProviderIds`。
- `version` 必须严格为 `1`。
- `seenProviderIds` 必须是去重、稳定排序且符合 Provider ID 格式的非空字符串数组；历史 ID 不要求仍存在于当前配置，避免 Provider 下架后把合法 State 误判为损坏。
- 文件不保存 Key、configured/missing 快照、账号、完成日期、应用版本、机器 ID、路径、选择历史或遥测。
- 目录/文件权限与 Secret Store 同级：macOS 目录 `0700`、文件 `0600`；Windows 权限按阶段三实机确认。
- 写入采用同目录临时文件 + 原子 rename；失败不得留下“已完成”的内存假状态。
- `markSeen(currentProviderIds)` 写入“既有合法 seen 集合 ∪ 当前 Provider ID”，不能因 Provider 暂时下架而删除历史 seen ID。
- 当前 Provider ID 必须来自已校验配置，不在 setup 触发逻辑中硬编码 `kimi/deepseek` 或数量 `2`。

首次与新增 Provider 判定：

```js
const currentProviderIds = config.providers.map((provider) => provider.id);
const state = await setupStateStore.read();
const unseenProviderIds = currentProviderIds.filter(
  (id) => !state.seenProviderIds.includes(id)
);
const shouldShowOnboarding = !state.exists || unseenProviderIds.length > 0;
```

等价实现可以不暴露 `exists`，但必须区分“合法空状态/文件不存在”和“已经看过所有当前 Provider”。

损坏 state 的处理与 Secret Store 不同，因为它不含凭据且不代表业务配置：

1. 输出不含原始文件内容的稳定 WARN。
2. 本轮把全部当前 Provider 视为 unseen，继续显示全量状态与向导。
3. 只有用户看过状态后完成、选择继续或明确稍后，才用合法 Schema 原子重建。
4. Ctrl+C、EOF 或其他错误不覆盖损坏文件。

完整 dashboard 入口（首次 `cmr` 或无参数 `cmr setup`）显示过全量状态并被用户明确结束后，可 mark seen。定向 `cmr setup <provider>` 和缺 Key Profile 的就地 setup 没有展示全量状态，不得把其他 Provider 标为 seen。

### 7.3 Setup 结果类型

不要让 `setup.js` 只返回不透明的数字，因为 `cli.js` 和 `launch.js` 需要区分“成功配置”“保留”“用户取消”“错误”。目标结果结构：

```js
{
  exitCode: 0 | 1 | 130,
  status: "configured" | "unchanged" | "cancelled" | "failed",
  configuredProviders: ["kimi"],
  changedProviders: ["kimi"],
  missingProviders: ["deepseek"],
  displayedProviderIds: ["kimi", "deepseek"],
  markedSeen: true | false
}
```

约束：

- 数组只含公开 Provider ID，不含 Key 或错误原文。
- `configuredProviders/missingProviders` 必须在返回前重新读取 Store 的真实状态，不能沿用开始时缓存。
- `changedProviders` 只记录本次成功写入项。
- `displayedProviderIds` 记录本轮真正显示过状态的 Provider；定向 setup 只含目标 ID。
- `markedSeen` 只有 full dashboard 已显示全部当前 Provider、用户明确结束且 State 写入成功时为 true。
- 用户选择“稍后/继续”返回 `exitCode: 0, status: "unchanged"`；full dashboard 同时 mark seen。
- Ctrl+C 返回 `130/cancelled`。
- 输入、Store 或配置失败返回 `1/failed`，并由统一错误出口脱敏。

允许使用等价命名，但 Luna 必须先在本文件回写偏差，不得把所有情况压成 boolean。

### 7.4 建议函数边界

`src/commands/setup.js` 至少导出等价接口：

```js
export async function runSetup(args = [], options = {})
export async function ensureProviderSecret(provider, options = {})
```

`runSetup()`：

- 解析范围只限空参数或单个 Provider ID；CLI 也可先解析，但不得两边语义不一致。
- 无 target 时显示全部当前 Provider 状态与管理菜单，并在用户明确结束时通过 injected `setupStateStore` mark seen。
- 有 target 时配置/替换该 Provider。
- 返回第 7.3 节结构。

`ensureProviderSecret()`：

- 先读取当前 Provider；存在则返回 unchanged，不提示。
- 缺失且非 TTY则返回 failed/抛出稳定的 missing 错误。
- 缺失且 TTY 时进入“required-for-launch”单 Provider 流程。
- 成功后重新读取并返回 secret 是否已配置；不得把 secret 放入返回结构。

如果 `launch.js` 需要实际 Key，应在 setup 成功后从传入的同一个 `secretStore` 再次 `get(provider.secretId)`，只在函数局部变量中使用。

`src/setup-state.js` 至少提供等价接口：

```js
export class SetupStateStore {
  async read()
  async getUnseenProviderIds(currentProviderIds)
  async markSeen(currentProviderIds)
}
```

该类只接收公开 Provider ID；不得 import SecretStore、读取 Key 状态或根据 configured/missing 决定 seen。

### 7.5 Prompter 依赖注入

不要在业务状态机里散落 `readline.question()`。建立一个最小可注入接口，例如：

```js
{
  choose({ message, choices, defaultId }),
  confirm({ message, defaultValue }),
  hidden({ message })
}
```

要求：

- production prompter 使用 Node 标准库与现有 `readHiddenSecret()`。
- tests 传 fake prompter，以 action ID 返回，不模拟脆弱的按键时序。
- 选择项使用稳定 ID（如 `all-missing/provider:<id>/continue`），Provider 动作由配置动态生成，显示数字只属于 UI。
- `confirm` 的替换默认必须是 `false`。
- 所有可见提示不拼接 secret。
- hidden label 只来自 `provider.displayName` 等已校验公开配置。

可以把可见 prompter 放在 `setup.js` 内部，只有在职责明显混乱时才新增 `src/prompter.js`。不要为三种提示引入通用 UI 框架。

### 7.6 Interactive 判定

在 `runCli()` 开头统一计算：

```js
const input = options.input ?? stdin;
const output = options.output ?? stdout;
const interactive = options.interactive ?? Boolean(input.isTTY && output.isTTY);
```

精确实现可调整，但必须：

- 测试注入的 input/output 生效，不能错误读取全局 `stdin/stdout.isTTY`。
- `interactive: false` 有最高优先级，确保 CI 不提示。
- setup 隐藏输入还必须验证 input 支持 `setRawMode`。
- 不因为 stderr 被重定向就把 Key 回退为可见输入。
- 不从 argv 猜测是否交互。

`interactive` 作为 option 传入 setup/launch，不要让各层用不同规则重复判断。

### 7.7 Secret Store 替换事务

复用现有 `SecretStore.set(provider, newSecret)`。替换合同：

1. 读取旧状态，只显示 configured/missing。
2. 若 configured，询问 `Replace the existing <Provider> API Key? [y/N]`。
3. 默认 No；No 返回 unchanged，不读取 hidden input。
4. Yes 后读取新值。
5. 先执行现有通用校验；任何失败都不调用 rename 覆盖目标。
6. 写同目录新临时文件，权限正确后 rename。
7. rename 成功才报告 configured。
8. 失败清理临时文件，旧目标文件内容/哈希保持不变。

严禁先调用删除、写空值或把旧 Provider 从 JSON 中移除。测试必须注入 `writeFile/chmod/rename` 各阶段失败，至少证明 rename 失败时旧值仍在。

注意：错误对象、AggregateError、临时路径和测试断言都不得包含新/旧 Key。替换成功后也不显示末四位或长度。

### 7.8 首次与新 Provider 触发合同

该判断只在无参数 TTY 路径使用，且顺序固定：

1. 加载并验证 Provider 配置，得到当前 Provider 集合。
2. 读取 Setup State，计算 unseen Provider。
3. State 缺失、损坏或 unseen 非空：读取 Secret Store 的**全部当前 Provider** 状态，进入 full dashboard setup。
4. 当前 Provider 全部 seen：读取实时 Key 状态，进入日常菜单。

Key 状态绝不改变第 3/4 步的首次判断：

- 零个 Key + State missing：引导。
- 一个 Key + State missing：同样引导，并显示一个 configured、其余 missing。
- 全部 Key + State missing：同样引导，并允许全部保留、分别更换或继续。
- Key 后来全部被移除 + all current providers seen：日常菜单显示 missing，不重新伪装成首次；选择 Provider 时就地 setup。
- 配置以后新增第三个 Provider + 旧 State 只 seen 两个：引导，并显示三个 Provider 的全量状态。

full dashboard 中用户完成配置、选择 `Continue` 或明确 `Not now` 后原子 mark 当前 Provider seen。Ctrl+C、EOF、Store 错误或 State 写入失败时不算完成；State 写入失败返回 1，已经安全写入的 Key 保留，但下次仍会再次引导。

### 7.9 普通菜单合同

普通菜单从当前 Provider/Profile 配置生成。`1.1.0` 当前示例至少包含：

```text
Claude Model Router
1) kimi — Kimi K3 [configured|missing]
2) deepseek — DeepSeek Auto [configured|missing]
3) setup — Configure or replace API Keys
4) doctor
5) exit
```

数字与标点允许按现有风格微调，语义不得变：

- 不显示密钥片段。
- 选择 configured Profile 直接启动。
- 选择 missing Profile 进入当前 Provider 的就地 setup。
- 选择 setup 进入管理向导；完成后刷新状态并回到普通菜单。
- 选择 doctor 只读执行并返回/退出，不触发 setup 写入。
- 无效输入不得默认为 exit 或某个 Profile；应给一次明确错误并允许重试，或稳定退出 1。选择一种并测试。

为了限制范围，菜单循环只需要支持“setup 完成后刷新一次并重新选择”。不要扩张成全屏 TUI、方向键或颜色框架。

### 7.10 Setup 菜单合同

首次/新 Provider 引导或无 target 的 `cmr setup` 都先显示当前配置中的全部 Provider。`1.1.0` 当前示例：

```text
API Keys are stored only in the local CMR secret store.
They are never written to this repository or shown in output.

kimi: configured|missing
deepseek: configured|missing
```

随后提供基于状态的动作：

- 有 missing 项：`Configure all missing providers (recommended)`。
- 为每个当前 Provider 动态生成 `Set or replace <displayName> API Key`。
- `Exit`。

当全部当前 Provider 都 configured 时，不显示虚假的“configure missing”；仍允许分别更换 Key，并提供 `Keep current API Keys and continue`。

`cmr setup kimi|deepseek` 跳过动作菜单，直接进入目标 Provider：

- missing：显示官方 URL 并隐藏输入。
- configured：先确认替换；默认 No。

定向语法从数据化 Provider ID 解析。当前 `cmr setup plan/build/kimi-k3/deepseek-auto` 不接受 Profile 别名；setup 管理的是 Provider secret ID，避免概念混乱。未来增加 Provider 时不应为 CLI 新增 `if` 分支。

### 7.11 Provider 配置步骤

每个 Provider 的固定步骤：

1. 显示 `provider.displayName` 与 `provider.apiKeyUrl`。
2. 提示用户先在官方平台创建/复制自己的 Key。
3. 不等待“我已打开浏览器”等多余确认；直接显示隐藏输入提示。
4. `readHiddenSecret()` 获取值；终端只换行，不显示字符或星号。
5. 调用 `SecretStore.set()`。
6. 成功只显示 `<id>: configured`。

对于“配置全部 missing”：

- 顺序固定使用配置加载器的稳定 Provider 顺序，测试不要依赖对象枚举偶然顺序。
- 每项成功立即提交。
- 第二项取消：返回 cancelled，第一项保留。
- 第二项失败：返回 failed，第一项保留。
- 重新运行时只处理仍 missing 的项，不询问替换第一项。

### 7.12 完成摘要

setup 结束后重新读取状态并显示：

```text
Setup summary
kimi: configured|missing
deepseek: configured|missing
Claude Code: found|not found
```

紧随摘要说明：`configured means stored locally; Provider access is checked when Claude Code connects.` 不得把 configured 翻译或扩写成 valid/verified/has balance。

若至少一家 configured 且 Claude found，显示：

```text
Next: run cmr kimi or cmr deepseek from your project directory.
```

只列已配置 Profile 也可以，但不得建议用户运行 missing Profile 而不说明会再次引导。

若 Claude not found：

- setup 已保存的 Key 仍算成功。
- 显示官方安装文档 `https://code.claude.com/docs/en/installation`。
- 不执行下载、npm、curl、winget、brew 或 PATH 修改。
- exitCode 仍由 setup 写入结果决定，不因 Claude 缺失把已保存 Key 回滚。

若 Doctor 可发现 Settings/Shell 冲突，不在 setup 中复制完整 Doctor 输出。完成摘要可显示一行：`Run cmr doctor before first launch if you have existing Claude provider settings.` 当前首版不自动调用迁移。

### 8.1 Help


保留：


## 9. 安全合同

### 9.1 Key 不得出现的位置

- CLI argv 与 Shell 历史。
- stdout/stderr/帮助/菜单/成功摘要。
- thrown error、cause、AggregateError、stack 的自定义 message。
- fake Claude 快照。
- 测试名、测试失败提示和 fixture 文件名。
- Git diff、README、docs、配置 JSON。
- `.env`、Claude Settings、Shell Profile、系统环境。
- Provider URL query、fragment、HTTP日志或遥测。

测试中可用明显假值，但断言失败时也避免把 actual raw Secret Store 整体打印出来。优先断言状态、哈希或单值等于预期假值。

### 9.2 终端安全

`readHiddenSecret()` 必须在以下每条路径恢复 raw mode、移除 listener 并 pause：

- Enter 成功。
- Ctrl+C。
- EOF (`end`)。
- `close`。
- stream `error`。
- `setEncoding` 失败。
- `setRawMode(true)` 失败。
- 超长输入。
- 后续 Store 校验/写入失败（此时 raw mode 应已经恢复）。

不要用星号回显；星号会泄漏长度且增加控制字符处理。不要在 Windows 为兼容回退到可见 `readline.question()`。

### 9.3 Store 损坏

如果 `secrets.json`：

- JSON 无效；
- Schema 无效；
- 含未知 Provider；
- 读取权限错误；

则 setup 显示脱敏错误并停止。不得把它视为空 Store、自动备份、覆盖、删除或“修复”。用户可用 `cmr config path` 定位；任何删除/恢复动作另行确认。

如果 `state.json` JSON/Schema 无效：

- 不读取或打印原始正文。
- 输出稳定 WARN，把全部当前 Provider 视为 unseen，继续展示全量 Key 状态。
- 只有用户明确完成/继续/稍后时才原子重建合法非敏感 state。
- Ctrl+C、EOF 或其他错误不覆盖原 state。

如果 State 读取因 `EACCES`、I/O 或路径类型错误失败，则返回 1 并停止，不把未知内容当作空状态，也不尝试覆盖。

`cmr config path` 在 `1.1.0` 应同时显示 Secret Store 与 Setup State 路径，便于诊断，但不读取内容。

### 9.4 替换恢复性

换 Key 失败的恢复标准是“旧 Key 仍可被 `get(provider)` 读取且目标文件内容不变”，不是仅仅“status 仍 configured”。错误实现可能写入截断或空值但 status 仍为 true，测试必须比较旧值或文件哈希。

### 9.5 Setup State 最小化

`state.json` 只允许保存 `version` 和 `seenProviderIds`。测试必须明确拒绝或证明实现不会写入：

- `configured/missing` 快照。
- Provider Key、Key 元数据或哈希。
- 用户名、邮箱、账号、组织或余额。
- 时间戳、安装版本、机器 ID、本机路径。
- 菜单选择、启动次数、Profile 使用记录或遥测。

### 9.6 本机边界

Luna 不得在开发机直接运行交互式 `cmr setup`，因为当前用户的真实 Secret Store 已配置。所有 setup 测试通过：

- `mkdtemp()` 创建临时 HOME。
- 显式传 `filePath` 的 `SecretStore`。
- fake prompter。
- `test-kimi-key` / `test-deepseek-key` 等假值。

运行 `node src/cli.js setup` 即使命令看似测试，也可能命中真实 HOME，属于红线；不要执行。

```text
API Keys stay in the local CMR secret store and are never shown in output.
```

## 13. 风险与控制

| 风险 | 根因 | 控制 |
|---|---|---|
| 安装卡死 | postinstall 无 TTY/后台执行 | 只在主动 `cmr` 运行时提示 |
| 已有 Key 的新用户跳过引导 | 用 Key 状态猜首次 | 独立 Setup State；State 缺失时无条件展示全量状态 |
| 升级用户被反复打扰 | 每次按包版本弹窗 | 只比较 current Provider 与 `seenProviderIds` |
| 新 Provider 无人知晓 | State 只存 completed boolean | seen ID 差集触发一次全量引导 |
| 换 Key 误删旧值 | 先清空再写 | default No + 单次原子 set + 失败旧文件不变测试 |
| Key 进入历史/进程列表 | 提供 argv flag | 禁止 `--key`，只允许 TTY hidden |
| Key 在错误中泄漏 | 拼接 input/error | 统一稳定错误，不把输入附加到 message/cause |
| Ctrl+C 后终端失常 | raw mode 未恢复 | hostile 事件矩阵 |
| 非 TTY CI 挂起 | 各模块自行判定交互 | CLI 统一 interactive，测试超时 |
| 多 Provider 中后项失败导致状态不明 | 多项一次性提交/回滚 | 逐项提交 + 重新读取摘要 |
| 假在线失败 | 代理/证书/Provider 波动 | 首版不联网验证 |
| 官方 Key 页面变化 | URL 写死在文案 | Provider `apiKeyUrl` + 发布前复核 |
| setup 破坏 Claude 参数 | 缺 Key 路径重构 launch | setup 后重新 get，原 `claudeArgs` 引用/副本不改 |
| setup 自动改旧配置 | 把“傻瓜式”误解为全自动迁移 | 只提示 Doctor；迁移另立门禁 |
| 损坏 Secret Store 被覆盖 | 把 parse error 当 missing | fail closed，不写 |
| 损坏 Setup State 永久阻断 | 把非敏感元数据当凭据 | WARN + 全量引导；明确完成后原子重建 |
| Windows 替换行为差异 | 文件 rename/TTY 不同 | fs failure injection + win32 模拟 + 阶段三实机 |

## 14. 门禁与停止规则
