## 1. 目标结果

### 1.1 用户体验

首个含 updater 的正式版本定为 `1.3.0`。

从 `1.3.0` 开始，受支持的全局安装用户执行：

```bash
cmr update
```

CMR 应完成：

```text
识别当前实际运行的 CMR 安装
  → 识别该安装自己的 npm prefix
  → 通过 npm 获取 GitHub 最新正式 Release 的固定包资产
  → 校验包名、稳定 SemVer 和版本方向
  → 已是最新版：不改安装，exit 0
  → 有新版：先把当前已安装包打包到临时目录作为本地回滚件
  → 从临时候选包更新同一个 prefix 中的 CMR
  → 用同一个绝对 cmr 入口验证新版本
  → 成功：报告 old → new，exit 0
  → 失败：验证旧安装；必要时用本地回滚包恢复，exit 1/130
```

只读检查：

```bash
cmr update --check
```

只报告当前版本与最新正式版本，不修改全局安装。

### 1.2 必须明确的 bootstrap

`1.2.1` 本身没有 `update` 命令，旧用户不可能在完全不改变本机代码的前提下直接执行 `cmr update`。

因此发布 `1.3.0` 时必须提供一次性手动升级命令：

```bash
npm install --global "https://github.com/zouerdong/ai-model-router/releases/download/v1.3.0/claude-model-router.tgz"
cmr version
cmr update --check
```

如果旧安装使用自定义 npm prefix，必须在一次性命令中显式使用相同 prefix：

```bash
npm install --global --prefix <current-prefix> "https://github.com/zouerdong/ai-model-router/releases/download/v1.3.0/claude-model-router.tgz"
```

从 `1.3.0` 升级到后续稳定版时，用户才进入完整的 `cmr update` 闭环。

### 1.3 支持结论

首版支持：

- macOS 上由 npm 安装到全局 prefix 的实体包目录。
- 原生 Windows 上由 npm 安装到全局 prefix 的实体包目录。
- 使用默认或自定义 npm prefix 的安装。
- 旧的 Git URL 全局安装，只要其最终是实体包而不是源码链接。
- GitHub Release `.tgz` 全局安装。
- 非交互终端中的显式 `cmr update` 与 `cmr update --check`。

首版不自动更新：

- `npm install --global .` / `npm link` 形成的本地源码 symlink/junction。
- 直接运行 `node src/cli.js` 的 checkout。
- Homebrew、WinGet、独立二进制或未来其他包管理器安装。
- 无法唯一确定当前命令、包根目录和 prefix 对应关系的安装。

这些情况必须 fail closed，打印对应维护方式，不能退化为 `git pull` 或更新 npm 的默认 prefix。

3. 对源码链接执行更新会直接改变开发工作流或解除链接，不能自动进行。

- `src/platform.js` 已有 PATH 大小写、Windows `.cmd/.bat` 与无 `shell: true` 的平台经验，但当前只定位 Claude。

## 3. 原始问题与根因

### 3.1 用户问题

用户已经安装 CMR 后，无法通过 CMR 自身获取新版本。当前每次升级都要求用户：

1. 知道 GitHub 出了什么版本。
2. 找回准确的安装命令。
3. 知道自己当时使用哪个 npm prefix。
4. 手工替换并验证。

这对非开发者不是完整的产品维护体验。

### 3.2 为什么“统一执行 git pull”不是正确修复

GitHub 是源码与 Release 来源，不等于每个安装目录都是 Git checkout。

按当前 README 使用 npm 安装 Git URL 后，用户通常得到 npm 展开的全局 package 和命令链接，不保证保留 `.git`。只有主动 clone 的开发者才有工作树，而这些工作树可能有：

- 本地修改。
- 非 `main` 分支。
- detached tag。
- 未提交文件。
- 自定义 remote。
- 与全局命令不同的另一份 clone。

因此 `cmr update` 自动执行 `git pull` 会同时产生两类错误：

- 对普通安装：没有仓库可拉。
- 对开发安装：可能修改或覆盖用户源码，并且不能证明更新的是当前命令。

根因不是缺一条 Git 命令，而是缺少：

- 稳定、机器可读的 Release package。
- 当前安装来源与 prefix 识别。
- 自替换前备份。
- 跨平台 npm 子进程边界。
- 更新后验证与失败恢复。
- 与发布操作绑定的资产完整性合同。

## 5. 关键设计决策

### D1 — 以 GitHub Release 固定资产为更新源

选择：

```text
latest release asset URL
  = https://github.com/zouerdong/ai-model-router/releases/latest/download/claude-model-router.tgz
```

不使用：

- GitHub `main` 分支。
- 最高 Git tag 直接猜最新。
- GitHub REST `/releases/latest` API。
- npm registry `latest`。

理由：

- Release 是“对用户可安装版本”的发布边界，不会把普通 main commit 当稳定版。
- draft/prerelease 不应进入 latest stable。
- 固定 asset URL 不需要运行时 GitHub API token，避开匿名 API rate limit。
- npm 自己负责 HTTPS、npm cache、用户已有代理/证书配置和 tarball 处理。
- 不依赖当前不可确认归属的 npm registry package 名称。

### D2 — Release 分发的是 `npm pack` 产物，不是仓库源码 archive

GitHub 自动 source archive 适合查看源码，但 updater 使用发布时生成并验收过的：

```text
claude-model-router.tgz
```

该资产必须来自同一 release commit 的 `npm pack`，内容与 `package.json::files` 一致。禁止把仓库目录随意压缩后改名冒充 package。

同时发布：

```text
SHA256SUMS
```

首版 updater 以 HTTPS、npm package 校验、固定 Release 和 immutable releases 为主要信任边界；`SHA256SUMS` 供发布审阅与人工恢复核对。若后续要让 updater 强制验证签名 manifest，另立安全规格。

### D3 — npm 只做 package transport 与安装，不做版本真相源

更新检查通过：

```text
npm pack <latest-release-asset-url> --json --ignore-scripts
```

取得候选 package metadata。必须验证：

- `name === "claude-model-router"`。
- `version` 是严格 `X.Y.Z` 稳定 SemVer。
- version 与当前版比较结果合法。
- 输出只有一个候选 package。
- 输出大小受限、JSON 可解析、字段类型严格。
- 实际 tgz 文件位于本轮临时目录内，是普通文件。
- tarball 实际大小与 npm 报告的 unpacked size 均受固定上限约束。

不得只因 `npm` exit 0 就信任任意 stdout。

### D4 — 下载到临时目录，再从本地 tgz 安装

实际 update 不直接让 npm 从 mutable `latest` URL 覆盖当前包。

流程：

1. 在受控临时目录用 npm pack 下载 latest asset。
2. 从结构化输出取得 candidate version 与本地 tgz 文件。
3. 校验候选。
4. 从本地 tgz 安装到精确 prefix。

这样 latest Release 即使在检查和安装之间变化，本次安装仍使用已经校验的同一份文件。

临时目录不得位于用户当前项目，不得读取项目 `.npmrc` 或生成 `package-lock.json`。

### D5 — 更新当前活动安装，不更新 npm 默认 prefix

安装识别必须从当前活动命令入口和 package root 出发，得到：

```text
{
  kind,
  platform,
  commandPath,
  packageRoot,
  prefix,
  packageName,
  currentVersion
}
```

macOS/Unix 标准结构：

```text
<prefix>/bin/cmr
<prefix>/lib/node_modules/claude-model-router/
```

Windows 标准结构：

```text
<prefix>\cmr.cmd
<prefix>\node_modules\claude-model-router\
```

算法必须处理：

- Unix bin symlink 指向 package entry。
- Windows `.cmd`/PowerShell shim 最终指向 package entry。
- 自定义 prefix。
- PATH 中存在多份 `cmr` 时只更新当前被调用的一份。

`npm prefix --global` 只能用于诊断交叉检查，不能覆盖从当前活动安装得到的 prefix。

### D6 — source-linked 安装 fail closed

若全局 package root 是 symlink/junction，或真实路径落入 Git checkout，判定：

```text
kind = source-link
```

行为：

- `cmr update --check` 可以报告 GitHub 最新版本，但同时标明当前安装不能自动替换。
- `cmr update` 在任何写操作前停止。
- 不执行 `git status`、`git pull` 或 npm relink。
- 输出建议开发者手工检查源码仓库，再决定 pull/test/reinstall。

不能通过 `--force` 绕过。

### D7 — 用户输入 `cmr update` 即是本次自更新授权

`cmr update` 是明确动作，不再增加第二次 `[y/N]`。

授权仅覆盖：

- 当前活动 CMR package。
- 该 package 所在精确 prefix。
- npm cache。
- 本轮临时目录与 update lock。

不覆盖：

- 其他全局 package。
- npm/Node/Claude 更新。
- 管理员提权。
- Git 工作树。
- Settings、Shell、系统环境或密钥。

Luna 开发和自动化阶段仍未获准修改维护机真实全局安装；运行时产品合同不能被用作开发会话越过红线的理由。

### D8 — 不自动提权

如果 prefix 不可写或 npm 返回 `EACCES`/Windows access denied：

- 不调用 `sudo`。
- 不触发 UAC。
- 不更改 prefix。
- 不回退到另一个 prefix。
- 输出当前安装 path/prefix、失败阶段和一条人工恢复命令。

### D9 — 更新前备份当前已安装 package

在覆盖前，用 npm pack 将当前实体 package root 打包到同一临时目录：

```text
rollback package = exact current installed package
```

要求：

- `--ignore-scripts`。
- backup metadata 的 name/version 与当前安装一致。
- backup tgz 在临时目录内。
- backup 完成前不得开始 install。

这样回滚不依赖旧 GitHub asset 是否可达，也不依赖 tag 是否仍存在。

### D10 — 安装后从精确入口验证

不能只运行 PATH 中的裸 `cmr`，因为 PATH 可能存在多份安装。

验证必须同时检查：

1. 目标 package root 的 `package.json`：
   - name 正确。
   - version 等于 candidate。
2. 更新前记录的同一 `commandPath`：
   - `cmr version` exit 0。
   - stdout 只有 candidate version。
3. commandPath 仍解析到目标 package。

验证期间不读取 Secret Store，不启动 setup，不启动 Claude。

### D11 — 失败时验证、回滚、再验证

失败分三层：

1. **下载/候选校验失败**：当前安装尚未修改，直接 exit 1。
2. **npm install 失败**：
   - 先用精确入口验证当前安装。
   - 若仍是 old version 且可运行，报告“更新失败，旧版仍可用”。
   - 若缺失、损坏或版本异常，用本地 rollback tgz 恢复。
3. **post-install 验证失败**：
   - 立即用本地 rollback tgz 恢复。
   - 再次验证 old version。

最终输出只能是：

- 更新成功。
- 更新失败但旧版仍可用。
- 更新失败，已恢复旧版。
- 更新与恢复均失败，需要人工执行精确恢复命令。

不得在失败后宣称成功，也不得吞掉 npm 非零退出码。

### D12 — 并发更新必须互斥

同一用户上下文同时只能有一个 `cmr update`。

建议 update lock：

```text
<CMR application data>/update.lock
```

合同：

- 以 exclusive create 获取。
- lock 只含 schema version、PID、startedAt 和随机 owner token；不含 Key、路径、账号或命令参数。
- 只有持有相同 owner token 的进程可正常清理自己的 lock。
- 新鲜 lock 存在时拒绝第二次更新。
- 新鲜但尚未写完、暂时无法解析的 lock 仍视为正在创建，不能直接删除。
- stale 判断阈值固定并测试；超过阈值但记录 PID 仍存活时继续拒绝并发。只有确认旧 owner 已不存活后才自动清理，并且必须重新 exclusive create，不能直接假定持锁成功。
- `--check` 不需要 lock。
- 成功、失败、Ctrl+C 和 rollback 后都走 `finally` 清理。

若实现者提出不做 lock，必须先提交 npm 同 prefix 并发安装不会破坏 package 的证据并等待用户修改本合同；不能静默省略。

### D13 — npm 子进程环境最小化但保留网络能力

npm 子进程：

- cwd 固定为本轮临时目录。
- cache 固定为本轮临时目录下的专用 npm cache；不依赖、修复或修改用户默认 npm cache。
- 使用 argv 数组。
- `shell: false`；Windows `.cmd/.bat` 只走显式 `cmd.exe /d /c`。
- 继承 stdio 的阶段与捕获 JSON 的阶段分开。
- 清除 Router 管理的 Anthropic/模型变量，避免无关 Provider 配置进入 npm。
- 保留 npm 所需的 PATH、代理、CA/certificate 与用户 npm 配置。
- 显式传 `--prefix`、`--ignore-scripts`、`--no-audit`、`--no-fund`。
- pack/install 都显式传 `--cache <temp-cache>`；即使用户默认 cache 损坏或含 root-owned 文件，也不能建议 updater 自动 `chown`。
- pack/install 捕获输出与运行时间必须有上限；不能先把任意大 stdout/stderr 全部读入内存后才校验 metadata。
- 不打印完整 env，不打印 `.npmrc`。

### D14 — 更新逻辑在替换前完整加载

Windows 自替换期间 package 文件可能被 npm 替换。实现不得在 install 成功后首次动态 import 旧 package 中尚未加载的 updater 模块。

开始 install 前必须已经加载：

- rollback 逻辑。
- verify 逻辑。
- platform spawn 逻辑。
- cleanup/lock 逻辑。
- 输出与错误映射。

install 后只能读取明确的新 package metadata、调用新 commandPath 或使用内存中已加载的旧代码完成回滚。

### D15 — 不自动检查更新

以下命令都不得隐式联网：

- `cmr`
- `cmr kimi`
- `cmr deepseek`
- `cmr list`
- `cmr doctor`
- `cmr version`
- `cmr setup`

只有显式：

```text

```

可以访问 GitHub/npm cache。

## 8. 建议接口合同

函数名可做等价微调，但职责不能混淆。

### 8.1 Version

```text
parseStableVersion(value)
compareStableVersions(left, right)
```

合同：

- 只接受 `0.0.0` 或无前导零的整数三元组。
- package version 不接受 `v` 前缀。
- 不接受 prerelease、build metadata、范围、空白和超大整数。
- 比较不能使用字符串字典序。

### 8.2 Pack metadata

```text
parseNpmPackMetadata(stdout, {
  expectedName,
  expectedDirectory,
  maxBytes
})
```

返回：

```text
{
  name,
  version,
  filename,
  tarballPath,
  integrity?,
  shasum?
}
```

必须拒绝：

- 非 JSON。
- 顶层不是单项数组。
- 缺 name/version/filename。
- 路径逃逸出 temp dir。
- symlink/目录而非普通 tgz 文件。
- 包名错误。
- unstable version。
- stdout 超限。

### 8.3 Installation inspection

```text
inspectCurrentInstallation({
  entryPath,
  modulePath,
  platform,
  fs,
  pathApi
})
```

返回：

```text
{
  kind: "global-package" | "source-link" | "unsupported",
  prefix,
  commandPath,
  packageRoot,
  currentVersion,
  reason?
}
```

要求：

- path 全部规范化。
- package root 的 package.json name/version 严格。
- global package path 与 commandPath 必须彼此一致。
- source symlink/junction 不解析后伪装为实体 package。
- 当前活动入口和默认 npm prefix 不一致时，以当前活动入口为准。

### 8.4 npm discovery/spawn

```text
findNpmExecutable(options)
buildCommandSpawnSpec(executable, options)
runNpm(args, options)
```

Windows：

```text
cmd.exe /d /c <npm.cmd> <args...>
shell: false
```

macOS：

```text
<npm> <args...>
shell: false
```

不得把 args join 成字符串。

### 8.5 Update plan

```text
planUpdate(currentVersion, candidateVersion)
```

只允许：

- `same`
- `upgrade`
- `candidate-older`

candidate older 必须拒绝，不自动降级。

### 8.6 Update result

建议稳定结果结构：

```text
{
  status:
    "already-current"
    | "update-available"
    | "updated"
    | "failed-old-intact"
    | "failed-rolled-back"
    | "failed-rollback",
  currentVersion,
  candidateVersion?,
  exitCode
}
```

不要把完整 child stdout/stderr、env、tarball 内容或 npm config 放入结果。

## 9. 精确更新事务

### 9.1 `cmr update --check`

1. 严格解析参数。
2. 读取 package/CLI 当前版本一致性。
3. 检查安装类型；source link 可继续查新版但标为不可自动更新。
4. 找 npm。
5. 创建隔离 temp cwd。
6. 运行 latest asset 的 npm pack dry-run/json/ignore-scripts。
7. 校验 metadata。
8. 比较版本。
9. 输出结果。
10. 清理 temp。

不得：

- 创建 update lock。
- 备份当前包。
- 调用 npm install。
- 修改 prefix。

### 9.2 `cmr update`

执行顺序固定：

1. 严格解析参数。
2. `inspectCurrentInstallation()`。
3. 非 `global-package` 时在网络和写操作前停止。
4. 读取并交叉检查 package/CLI current version。
5. 查找 npm。
6. 获取 update lock。
7. 创建 temp directory。
8. 将当前 package root 用 npm pack 保存为 rollback tgz。
9. 校验 rollback name/version/path。
10. 从 latest Release 固定 URL pack candidate 到 temp。
11. 校验 candidate name/version/path。
12. candidate == current：不 install，正常退出。
13. candidate < current：拒绝 downgrade。
14. 再次确认当前 command/package/prefix 未在等待期间变化。
15. 用本地 candidate tgz 执行精确 prefix 的 global install。
16. 验证新 package.json 与绝对 commandPath version。
17. 成功后报告 old → new。
18. 任一 install/post-verify 异常按 D11 处理。
19. `finally` 清理 lock 和 temp。

### 9.3 npm argv 基线

备份当前 package：

```text
npm pack <current-package-root>
  --json
  --ignore-scripts
  --cache <temp-cache>
  --pack-destination <temp>
```

获取 candidate：

```text
npm pack <latest-release-asset-url>
  --json
  --ignore-scripts
  --cache <temp-cache>
  --pack-destination <temp>
```

安装：

```text
npm install
  --global
  --prefix <exact-current-prefix>
  --ignore-scripts
  --no-audit
  --no-fund
  --cache <temp-cache>
  <local-candidate-tgz>
```

rollback 使用同样 install flags，只把最后参数换成本地 rollback tgz。

实际代码必须使用 argv 数组；上述换行只是合同展示。

### 9.4 信号

- pack/install child 运行时，Ctrl+C 必须终止当前 update 路径。
- 不留下继续运行的 npm 子进程。
- 已转发的 SIGINT 由 CMR 记录；即使 npm 最终返回普通非零码，对外仍返回 `130`。
- 中断发生在 install 前：旧安装不变。
- 中断发生在 install 中：验证旧安装，必要时 rollback。
- 退出码最终为 `130`，但 rollback 结果仍要报告。
- SIGTERM/SIGHUP 的跨平台行为按现有 launcher 经验测试，不得使用 `shell: true` 绕过。

## 12. 测试设计细节

### 12.1 单元测试不能依赖公网

默认 `npm test`：

- 不请求 GitHub。
- 不读真实 HOME。
- 不修改真实 npm cache/prefix。
- 不运行真实全局 install。

latest asset、npm runner、fs、clock、random token、lock、platform、entryPath、modulePath 全部可注入。

### 12.2 E2E 使用临时 prefix

每个 E2E 创建：

```text
temp HOME
temp APPDATA / application data
temp npm cache
temp npm prefix
temp package fixtures
temp release-asset directory or local HTTP fixture
```

测试退出后比较：

- 目标 prefix package version。
- 非目标 prefix 哈希/清单。
- Secret/State 不存在或哈希不变。
- lifecycle sentinel 不存在。
- lock/temp 无残留。

测试临时目录由 test framework cleanup；若清理失败只报告路径，不在仓库创建补丁文件。

### 12.3 Windows OS E2E 矩阵

至少运行：

1. PowerShell：`cmr update --check`。
2. PowerShell：临时 prefix old → candidate。
3. CMD：临时 prefix old → candidate。
4. Git Bash：调用 Windows npm.cmd 的临时 prefix场景。
5. 路径含空格和中文。
6. `%APPDATA%` 临时路径。
7. Ctrl+C。
8. install failure → rollback。
9. source junction 拒绝。
10. 同机多 prefix。

这里的“Windows OS”允许物理机、本地 Windows VM 或 GitHub-hosted Windows VM；验收关注 Windows 内核、文件系统、`.cmd`、PowerShell/CMD/Git Bash 与进程行为，不要求物理硬件。不得用 Mac 的 `platform: "win32"` 注入替代这些结果。托管运行必须记录 runner image、Windows/Node/npm/Git 版本、commit SHA、run URL、测试输出和候选包 hash。

### 12.4 Release candidate 验证

在正式 publish 前，从 release draft 下载固定资产到全新临时目录：

1. 核对 SHA-256。
2. `npm pack`/tar 清单核对。
3. 安装到全新 temp prefix。
4. `cmr version`。
5. `cmr help`。
6. `cmr update --check` 指向 draft 时不可作为 public latest 证据；使用精确 candidate fixture 完成功能验证。
7. 发布后再用 public latest URL 做非破坏性 `--check`。

## 13. 风险与控制

| 风险 | 根因 | 控制 |
|---|---|---|
| `git pull` 无仓库或覆盖源码 | 安装与 clone 混淆 | Release tgz；source link 拒绝 |
| 更新到错误 prefix | npm 默认 prefix 与活动命令不同 | 从活动入口反推并交叉验证 |
| 更新到未发布 main commit | main 不是 release channel | latest Release fixed asset |
| GitHub API 限流 | 匿名 REST 额度 | 不依赖 REST；latest asset URL |
| 用户默认 npm cache 损坏或 root-owned | 历史 npm 权限问题 | 本轮 temp cache；不 chown、不改 npm config |
| 最新跳转在安装中变化 | check/install TOCTOU | 先 pack 到 temp，再本地安装 |
| 远端 scripts 执行 | npm lifecycle | 全路径 `--ignore-scripts` + sentinel |
| Windows 自替换失败 | shim/文件锁差异 | 预加载逻辑、绝对入口、Windows E2E、rollback |
| custom prefix 被忽略 | 盲用 `npm prefix -g` | 当前入口为真相源 |
| install 失败后命令损坏 | npm 替换非业务事务 | 本地 rollback tgz + verify |
| 两次 update 并发 | 同 prefix 并发写 | exclusive update lock |
| 权限不足时装到另一处 | npm fallback/错误处理不当 | exact prefix、no sudo、fail closed |
| 更新泄露 Key | 继承/打印完整 env | 清除 Router vars、不读 Store、脱敏 |
| Release asset 被替换 | 可变 tag/asset | draft 先装资产；immutable publish |
| 旧用户以为 `1.2.1` 可直接 update | bootstrap 悖论 | 一次性手动 `1.3.0` 命令 |
| 源码用户失去开发修改 | 全局 link 指向 checkout | source-linked 自动更新禁用 |

### 18.3 审阅发现与修复

本轮没有保留临时补丁；修复均围绕根因并补充回归：

1. 修复半写新锁会被并发进程误判陈旧并删除，以及仅按年龄删除仍由活进程持有的锁。

7. 为 pack/install/version 子进程加入超时和 stdout/stderr 捕获上限，避免卡死与内存无界增长。
8. 修复临时 workspace 的 cache 创建失败时残留半成品目录，以及 lock/check 清理失败静默丢失的问题。
