## 0. 一页结论

### 0.1 本轮绑定范围

`1.4.0` 只新增一个正式入口：

```bash
cmr glm [claude args...]
```

它表示：

- Provider ID：`glm`
- Profile ID：`glm`
- 显示名：`GLM-5.2 Coding Plan`
- 兼容别名：`glm-5.2`、`glm-plan`
- 目标区域：智谱中国区
- 目标产品：GLM Coding Plan
- Anthropic 兼容 Base URL：`https://open.bigmodel.cn/api/anthropic`
- 鉴权变量：`ANTHROPIC_AUTH_TOKEN`
- Secret Store ID：`glm`

本轮**不新增**：

```bash
cmr glm-api
cmr zhipu-api
cmr glm-payg
```

也不实现 Coding Plan 额度耗尽后自动切换按量 API。按量 API 的差异与未来方案记录在本文第 13 节，但不属于 Luna 本轮授权范围。

### 0.2 为什么只做 Coding Plan

用户的最终目标是使用 GLM Coding Plan。官方资料显示，Coding Plan 与标准按量 API 虽然都存在 Anthropic 兼容接入方式，但至少有三项不能混为一谈：

1. Coding Plan 的 Claude Code 官方配置使用 `ANTHROPIC_AUTH_TOKEN`，Claude Code 会发送 `Authorization: Bearer`。
2. 标准 API 文档建议使用 `ANTHROPIC_API_KEY`，Claude Code 会发送 `X-Api-Key`。
3. Coding Plan 使用套餐额度并且额度耗尽后不会自动扣账户余额；标准 API 按 Token 从资源包/余额扣费。

同一个 Base URL 不等于同一种凭据、同一个账单通道或同一套失败语义。没有真实证据前，不能把两者压成一个“万能 GLM Key”入口。

### 0.3 可以在没有真实 Plan Key 时完成什么

在用户尚未抢到 Coding Plan 时，Luna仍可完成：

- 仓库内 Provider/Profile/Pricing 配置。
- 配置 Schema 与加载器改造。
- Setup State 新 Provider 触发。
- Secret Store 的三 Provider 兼容。
- CLI、Doctor、List、Help 与菜单。
- 假 Claude 的环境、argv、cwd、TTY、信号和退出码回归。
- Mac 自动化、Node 18 兼容审查、Windows 模拟与打包检查。

但在用户取得 Plan Key 并明确授权真实调用前，不得宣称：

- GLM Key 有效。
- `cmr glm` 已真实连接。
- 实际扣的是 Coding Plan 而不是余额。
- 主会话、工具或子 Agent 已真实使用 GLM-5.2。
- `1.4.0` 已完成 Provider 验收或可以正式发布。

因此 Luna 的正常交回状态应是：

```text
LUNA_IMPLEMENTATION_COMPLETE — AWAITING_GLM_PLAN_ACCEPTANCE
```

而不是 PASS。

## 2. Coding Plan 与标准按量 API：部署差异

核验日期：2026-07-28。

| 维度 | GLM Coding Plan（本轮） | 智谱标准按量 API（后续） |
|---|---|---|
| 主要用途 | 官方支持的 Coding Agent 工具 | 自建应用、网站、机器人、SaaS、SDK/API 集成 |
| Claude Code Anthropic Base URL | `https://open.bigmodel.cn/api/anthropic` | 官方 Claude 兼容文档也给出 `https://open.bigmodel.cn/api/anthropic` |
| Claude Code 凭据变量 | `ANTHROPIC_AUTH_TOKEN` | 标准 API 文档建议 `ANTHROPIC_API_KEY` |
| Claude Code 实际 Header | `Authorization: Bearer <value>` | `X-Api-Key: <value>` |
| Key 获取 | 个人套餐概览；团队套餐使用单独团队 Key | 标准 API Keys 页面 |
| 计费 | 每 5 小时 + 每周套餐额度 | Token 单价，优先资源包再余额 |
| 额度耗尽 | 不自动扣其他资源包/余额 | 余额或适用资源包不足时失败 |
| 使用范围 | 仅官方支持的工具/产品 | 标准 API 协议允许的应用集成 |
| GLM-5.2 额度权重 | 高峰/非高峰可能按套餐系数消耗，活动规则会变化 | 按实际输入、输出、缓存 Token 单价 |
| CMR 应否自动互相回退 | 否 | 否 |

### 2.1 当前可确认的官方事实

- Coding Plan Anthropic Message 端点是 `https://open.bigmodel.cn/api/anthropic`。
- Coding Plan Claude Code 配置示例使用 `ANTHROPIC_AUTH_TOKEN`。
- Claude Code 官方说明 `ANTHROPIC_AUTH_TOKEN` 被发送为 Bearer Header。
- 智谱标准 Claude 兼容文档建议 `ANTHROPIC_API_KEY`。
- Claude Code 官方说明 `ANTHROPIC_API_KEY` 被发送为 `X-Api-Key`。
- 标准 API 的 GLM-5.2 原生模型 ID 是 `glm-5.2`。
- GLM-5.2 标准 API 当前公开价格为：缓存命中 ¥2/M、普通输入 ¥8/M、输出 ¥28/M Token。
- GLM-5.2 为 1,000,000 Token 上下文，最大输出 128K Token。
- Coding Plan 额度耗尽后不会自动扣用户其他资源包或余额。
- 团队 Coding Plan Key 与平台其他 API Key 不通用。

### 2.2 当前不能替用户承诺的事实

官方页面没有给 CMR 提供一个本地可判定的“这把 Key 一定走 Plan”的离线字段。CMR setup 只保存字符串，也不联网验证。因此：

- `configured` 仍只表示已存入本机 Store。
- CMR 不根据 Key 前缀判断 Plan/PAYG。
- CMR 不根据账号余额推断账单通道。
- CMR 不展示“Plan verified”。
- 实际扣费通道必须在一次获批的最小真实请求后，通过智谱费用明细/套餐用量回读确认。

### 2.3 为什么不能自动降级到按量 API

自动降级会同时违反三个现有产品边界：

1. CMR 不做请求级动态路由或失败重试代理。
2. 从套餐额度切到现金余额属于有实际费用后果的决策，不能隐式发生。
3. 两种凭据 Header 不同；“第一次 429/1113 后换变量重试”会扩大密钥与账单风险。

若未来需要 `glm-api`，它必须是用户显式选择的独立 Profile，不是 `glm` 的隐藏 fallback。

## 3. 产品合同

### 3.1 新入口

```bash
cmr glm [claude args...]
cmr glm-5.2 [claude args...]
cmr glm-plan [claude args...]
```

三者环境和 argv 行为必须一致。规范 ID 是 `glm`；另外两个只是数据化别名。

代表性用法：

```bash
cmr glm
cmr glm --continue
cmr glm --resume <session-id>
cmr glm --fork-session --resume <session-id>
cmr glm --permission-mode plan
cmr glm -p "分析并修改这个项目"
cmr glm --model <provider-supported-model>
cmr glm --help
```

CMR 不解析、记录、改写或过滤 Profile 后参数。

### 3.2 模型映射语义

本轮采用智谱中国区完整 Claude Code 指南当前给出的映射：

```text
ANTHROPIC_DEFAULT_OPUS_MODEL=glm-5.2[1m]
ANTHROPIC_DEFAULT_SONNET_MODEL=glm-5.2[1m]
ANTHROPIC_DEFAULT_HAIKU_MODEL=glm-4.7
CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
API_TIMEOUT_MS=3000000
```

Provider 再注入：

```text
ANTHROPIC_BASE_URL=https://open.bigmodel.cn/api/anthropic
ANTHROPIC_AUTH_TOKEN=<GLM Coding Plan Key>
```

### 3.3 明确禁止自行补齐的变量

初始候选不得加入：

```text
ANTHROPIC_MODEL
ANTHROPIC_DEFAULT_FABLE_MODEL
CLAUDE_CODE_SUBAGENT_MODEL
CLAUDE_CODE_EFFORT_LEVEL
ENABLE_TOOL_SEARCH
```

理由：

- 当前智谱 Claude Code 完整配置没有列出这些键。
- `ANTHROPIC_MODEL` 缺失时，Claude Code 仍按默认档位选择并应用 Sonnet/Opus 映射；不能凭其他 Provider 经验强行复制。
- 智谱文档建议在会话内用 `/effort` 选择 max，但没有在当前完整配置中要求 `CLAUDE_CODE_EFFORT_LEVEL`。
- 子 Agent 的实际档位必须通过假环境和获批的真实验收观察，不能先写死再宣称完整。

若真实验收证明主会话或子 Agent 未按官方预期落到 GLM 模型，停止并报告证据。先更新 `docs/07` 与本文的映射合同，经用户确认后再改代码。

### 3.4 `[1m]` 的协议层级

`glm-5.2[1m]` 是 Claude Code 的模型选择值；智谱标准 API 原生模型 ID 是 `glm-5.2`。CMR 不剥离 `[1m]`，也不建立代理转换层。

验收必须区分：

```text
Claude Code 环境/状态层：glm-5.2[1m]
智谱上游模型层：glm-5.2
```

不得把手工直连接口时发送 `glm-5.2[1m]` 的失败，直接归咎于 CMR。

### 3.5 新用户与升级用户

- 全新用户首次运行 `cmr`：看到 Kimi、DeepSeek、GLM 三家完整状态。
- `1.3.0` 升级用户的 `state.json` 已 seen `kimi/deepseek`：因为 `glm` unseen，再次进入一次全量 onboarding。
- 用户可选择稍后，不强制先有 GLM Key。
- `cmr setup glm`：定向配置或更换 GLM Key，不把其他 Provider 标为 seen。
- `cmr glm` 缺 Key + TTY：就地只配置 GLM，成功后继续原启动。
- `cmr glm` 缺 Key + non-TTY：快速失败，不等待输入。
- `cmr secret set glm` 与 `cmr secret status` 必须支持 GLM。

```js
ENABLE_TOOL_SEARCH
```

这样后续官方事实变化时，变更会表现为显式测试差异，而不是静默混入。

## 7. 关键架构决策

### 7.1 仍是一个独立 Provider

`glm` 需要独立 Key，因此必须新增 Provider ID，而不是只在现有 Kimi/DeepSeek Provider 下新增 Profile。这样 Setup State 才会把 GLM 识别为 unseen，Secret Store 才有独立槽位。

### 7.2 不迁移 Secret Store Schema

继续使用：

```json
{
  "version": 1,
  "providers": {
    "kimi": "...",
    "deepseek": "...",
    "glm": "..."
  }
}
```

兼容要求：

- 只有 Kimi/DeepSeek 的旧 Schema v1 文件仍可读。
- 添加 GLM 时旧两项字节值不变。
- GLM 写入失败时旧两项保持可读。
- 不增加凭据类型、账单模式、Key 来源或 Plan 状态字段。

### 7.3 Setup State 无 Schema 迁移

旧状态：

```json
{
  "version": 1,
  "seenProviderIds": ["deepseek", "kimi"]
}
```

在新配置下自然产生：

```text
unseenProviderIds=["glm"]
```

完成或明确稍后后，写为：

```json
{
  "version": 1,
  "seenProviderIds": ["deepseek", "glm", "kimi"]
}
```

不得加 `onboardingVersion`、`glmSeen` 或包版本特判。

### 7.4 两个 GLM 附加环境变量进入 Router 管理集合

`API_TIMEOUT_MS` 与 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 一旦进入正式 GLM Profile，就属于 Router 管理的 Provider/Profile 环境。必须遵守项目现行隔离合同：每次启动先从继承环境中清除全部 Router 管理变量，再只注入当前选中 Provider/Profile 的值。

因此实现要求：

1. 把两个键加入允许的 Profile 环境变量集合。
2. 同时把两个键加入 `ROUTER_MANAGED_ENV_VARS`。
3. 每个 Profile 启动时，大小写不敏感地删除父环境中的同名变体。
4. 选中 GLM 时再注入官方值；选中 Kimi/DeepSeek 时不回注，因此其子进程中这两个键应不存在。
5. 不修改 `process.env`。

这会有意覆盖用户父环境中同名的全局 Claude Code 偏好，原因不是 GLM 特例，而是 CMR 的核心产品合同要求 Provider/Profile 环境互相隔离。若未来希望支持用户级透传白名单，应另立通用规格，不能在本轮给两个键加例外。

### 7.5 现有两家仍需硬基线，新增集合不能散落

当前加载器、validator、secret 命令和 Doctor 各自有两家硬编码。Luna应把“当前正式发布集合”收敛为少量清晰常量或同一加载集合，不得在更多模块继续复制 `["kimi", "deepseek", "glm"]`。

允许的最小实现：

```js
const PROVIDER_IDS = Object.freeze(["kimi", "deepseek", "glm"]);
const PROFILE_IDS = Object.freeze(["kimi", "deepseek", "glm"]);
const PRICING_IDS = Object.freeze(["kimi-k3", "deepseek-v4", "glm-5.2"]);
```

并让 CLI/Doctor/SecretStore 从已校验的 `config.providers` 派生 Provider IDs。不要在 setup/menu 逻辑中写三家 `if` 分支。

### 7.6 版本与发布

新增用户可见 Provider/Profile 是向后兼容的 minor 功能，候选版本为 `1.4.0`。Updater 不需要新增 GLM 分支；它只负责安装整个候选包。

发布仍必须走 `docs/13` 已验收的固定资产、checksum、exact/latest、Windows T4 与 immutable Release 流程。本文件不授权发布动作。

## 12. 风险、兼容与回退

### 12.1 降级到 `1.3.0` 的 Secret Store 风险

`1.4.0` 写入 `glm` 后，旧 `1.3.0` 的 Secret Store 允许集合不认识 `glm`，手工降级可能导致旧版把 Store 判为 invalid。

控制：

- 自动更新的 install/verify rollback 发生在用户运行新版本 setup 之前，通常不会遇到已写 GLM Key。
- 发布文档必须明确：使用 GLM Key 后手工降级需要先制定脱敏备份与 Store 兼容方案。
- 不得为了兼容降级自动删除 `glm` 字段。
- 任何备份、覆盖、删除或 Key 轮换都需用户确认。
- `1.4.0` 本身应继续 fail closed，不静默忽略未知 Secret 字段。

### 12.2 官方配置变化

模型名、Base URL、价格、额度系数和 Key 页面都是可变事实。运行时不能把价格/活动日期写进 JS 分支。事实变化先更新配置与 `docs/07`，再更新测试。

### 12.3 GLM Profile 与用户显式 `--model`

用户可执行：

```bash
cmr glm --model <value>
```

CMR 不校验 Provider 是否支持该模型。失败由 Claude Code/智谱返回。文档不得承诺任意 `--model` 都能使用 Plan 额度。

### 12.4 Settings 覆盖

用户或公司 Settings 可能覆盖 GLM env。Doctor 只读报告键名；setup 不自动迁移或删除。需要改 Settings 时另立门禁与备份方案。

### 12.5 Plan Key 与团队 Key

团队 Key 官方明确与平台其他 Key 不通用。CMR只保存一个 `glm` secret slot；用户从正确套餐入口取得自己的 Key。CMR不存团队 ID、成员 ID 或 Key 类型。

## 13. 标准按量 API 的后续方案（本轮禁止实现）

如果用户未来明确要求同时保留 Coding Plan 与按量 API，应另开候选版本，建议：

```text
Provider/Profile: glm-api
Base URL: https://open.bigmodel.cn/api/anthropic
authVariable: ANTHROPIC_API_KEY
secretId: glm-api
apiKeyUrl: https://bigmodel.cn/usercenter/proj-mgmt/apikeys

```

必须是独立 Profile 的原因：

- Header 与 Coding Plan 不同。
- Key 获取入口不同。
- 费用后果不同。
- 用户需要显式知道本次选择的是套餐还是按量。
- 两把 Key 需要独立替换和撤销。

后续规格还必须先解决：

1. 是否把 `glm-api` 标为可选 Provider，避免 onboarding 推荐用户配置两把 GLM Key。
2. 标准 API Key 在 Claude Code 当前版本、当前中国区 endpoint 的真实 E2E。
3. 资源包、现金余额与 Claude Code 的实际扣费顺序。
4. `ANTHROPIC_API_KEY` 交互确认对 CMR 用户体验的影响。
5. Plan 与 API 两 Profile 的菜单文案和误选费用警告。
6. 明确禁止自动 fallback。

在这些问题未形成新规格前，Luna不得创建 `glm-api.json`。
